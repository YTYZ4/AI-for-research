## 项目目标

面向有基本数学知识的学生，将自然语言问题和可选数据转为假设、变量、数学模型、可执行求解及验证报告。核心研究问题是：相较于普通大模型求解，结构化建模与可执行验证是否改善不同题型的端到端求解成功率？

采用现成大模型与本地求解工具；参数微调、概率仿真、复杂多智能体系统、账户管理和云部署不列为八周必交付项。支持四类任务不等于具备通用数学建模能力；正式教学效果不在本轮结论范围内。

## 系统设计

统一流程：信息检查 → 建模草案 → 用户检查/编辑 → 求解 → 验证 → 有限修复 → 解释与导出。

1. 问题理解：提取输入、目标和约束，缺少必要数据时澄清，超出能力范围时明确说明。
2. 数学模型：结构化表达变量、单位、假设、目标、约束或方程；可保存、编辑和重放。
3. 求解工具：每类实现求解适配层；第一周只支持非负变量的线性/混合整数生产计划。
4. 验证：独立复算约束、目标、残差、守恒或任务特有性质。区分给定模型的数值可行与原题建模正确。
5. 修复：最终版本最多两轮，保存失败及修改记录；不隐瞒失败，不从保留评分器获取提示。
6. 报告：展示模型、结果、验证状态、限制和成本；支持本地运行与导出。

第一周仅将模型作为数据交给受控求解函数，不执行模型生成代码。后续若增加任意代码执行，必须先实现独立执行环境、超时和资源限制。第一周不是任意 Python 代码沙箱。

## 实验设计

### 跨题型主实验

三种条件使用同一模型版本、输入数据和求解工具：

| 条件 | 处理方式 | 比较目的 |
|---|---|---|
| A 普通求解 | 普通分析并调用工具，允许普通执行反馈 | 基线 |
| B 结构化建模 | 显式表达变量、假设、目标和约束 | 建模流程的增量 |
| C 建模加验证反馈 | B 加通用检查和有限修复 | 验证反馈的增量 |

12 道保留题 × 3 条件 × 3 重复 = 108 次任务运行。为三组设置相同的调用/修复上限和 token 上限（开发试跑后填写固定配置），同时记录实际开销。不能让 C 仅靠更多尝试次数占优。

主要指标：端到端成功率、建模正确性、求解有效性、token/调用量/耗时/修复次数。连续任务采用误差与可接受阈值，优化任务报告可行性和目标值差距。类别内先汇总，再计算四类等权平均；同题重复不能当作独立题目。小样本结果报告计数、逐题表现与不确定性，不预设显著提升。

### 错误识别与修复实验

每类 3 个错误版本，共 12 个。覆盖漏约束、整数性错误、数据泄漏、只看训练误差、初值/符号错误、有向图和容量错误。开发调试所用错误另建，正式评测错误版本保留，不用来反复调规则。

12 个错误版本 × 2 条件（普通执行反馈/结构化验证反馈）× 3 重复 = 72 次修复运行。报告检出率、修复成功率、新错误比例；另用正确实现测量误报。必须包含“能运行但数学模型错误”的版本。

### 信息不足和条件变化检查

预先定义 8 个场景：优化新增产量上限、不可行订单；拟合单位变化、缺失输入列；动态系统初值缺失、参数变化；网络任务断路、容量变化。提供固定补充信息脚本，避免不同条件获得不同数据。作为实用案例分析，单独计数。

### 独立评价

- 数值、约束和结构以独立程序为主；允许等价正确解。
- 建模与解释采用预先固定的人工评分规则，尽可能隐藏方法标签。
- 助手运行时验证器不读取参考答案或隐藏评分器。
- 记录模型版本、输入、配置、原始响应、数学模型、工具输出、修复轨迹与耗时；API 密钥不进日志。
- 技术回归测试不算大模型实验，模板解析运行不算模型生成数据。
- 开发阶段先跑 12 次 API 任务测量成本，再决定正式批量规模；180 次指完整任务，不是 API 请求数。预算暂未确定，不自动发起批量付费实验。
