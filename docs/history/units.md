# 动态时间单位的确定性换算与回归

2026-10-16，版本0.8.0。针对上一轮Logistic“每天0.2、720小时”被模型错误换算的问题，将动态时间换算从模型推理移交本地程序。

## 实现

在线动态模型只返回dynamics_input，包含原题initial、equilibrium、rate、rate_unit、duration、duration_unit，以及四个数值的原文source_quotes。提示要求只提取、不换算；程序核对引用存在于输入、原数字出现在对应引用中、时间单位与引用相符。仍有语义错配可能，引用检查不等于完整自然语言验证。

程序保留原速率和单位，把时长换到该速率的分母单位：

- 0.2/天、720小时 → 速率仍0.2/天，时长720×(3600/86400)=30天。
- 0.1/分钟、0.5小时 → 速率仍0.1/分钟，时长0.5×60=30分钟。

转换使用固定秒/分/小时/天比例与Decimal运算，不调用大模型。没有默认跨年换算：若年与其他单位混用，要求明确口径而非自动假设365天。当前针对两类动态系统的时间/速率，尚未接管图网络长度、优化资源或温度单位换算。

成功运行同时保存：

- source_model.json：原题数值、各自单位、原文引用；保持不变。
- unit_conversion.json：转换因子、原值、结果、引用是否核对。
- model.json：实际用于求解的规范化模型。
- run.json：请求、原始响应、上述过程及结果；报告并列原始参数和换算参数。

旧的规范化dynamics文件仍可通过--model-file离线求解。在线若模型返回没有原题参数的旧格式，不再默默接受，会要求核对来源。手工source模型可离线转换，但会标source_quotes_checked=false，因为没有可核对的原始题面。

## 真实回归结果

两种混合单位题、两个正常对照，每题三次，共12次DeepSeek调用，无重试。用量37,047 tokens。

| 场景 | 原始判定 | 离线复核后 |
|---|---:|---:|
| 正常牛顿冷却 | 3/3 | 3/3 |
| 正常Logistic | 3/3 | 3/3 |
| 冷却分钟/小时混合 | 1/3 | 2/3 |
| Logistic天/小时混合 | 3/3 | 3/3 |
| 合计 | 10/12 | 11/12 |

Logistic先前的换算错误本轮未复现：3次均提取原值0.2/天和720小时，程序输出30天，终值约978.17805个。所有实际执行的11条动态结果中，原始参数、程序换算和原题解析轨迹均通过。

两项异常区别处理：

1. 冷却混合题第1次输出celsius。原评分器只接受Celsius等固定大小写，误判状态单位；补大小写等价处理后离线复核通过。原始10/12保留，11/12是单独审计结果，没有重新调用。
2. 冷却混合题第3次在JSON顶层额外输出model_type字段，不符合严格schema。原始数值本身看起来正确，但整个响应未通过解析，也没有执行；保留为真实格式失败，不通过删除字段来伪造原始通过。

因此可以说“已将动态时间换算交给程序，原Logistic换算错误本轮3/3修复验收通过”，不能说“所有输入都稳定”或“12/12端到端通过”。三次仍不足以证明长期稳定。

## 程序验证

77项测试通过。新增原始参数不被改写、天/小时与分钟/小时换算、原题数值或引用不符拒绝、不同单位提取错误拒绝、跨年不默认换算、积分资源限制按转换后的时长检查、摄氏度别名大小写兼容。现有坏CSV、非法参数、交互修正以及其他三类任务回归保持通过。

下一步优先解决结构化响应的格式波动（保留原始响应并单独统计任何修复），再扩展其他量纲；不要把它与已经确定化的时间运算混为一个问题。
